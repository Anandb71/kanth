# DECISIONS

Every decision that shaped Kanth, with the reason. Where we overruled the original brief, it says so.

## Product

**1. Keep the Kanth idea.** We generated 32 candidates and researched the five strongest challengers. None beat Kanth by a clear margin with evidence. See [IDEAS.md](IDEAS.md).

**2. Bulbul speaks as the user, never on its own.** Nothing is played in the user's voice unless the user chose it. Prespoken audio is stored, never played. In code, the only calls that play the user's channel are `choose()` and `speakText()` in [web/src/lib/kanth.ts](web/src/lib/kanth.ts). In demo mode the viewer chooses; in the recorded film a simulated user chooses, and the screen says so.

**3. Overruled the brief: the default voice is a Bulbul V4 Flash persona, not a cloned voice.** Measured: the cloning endpoints ignore the `model` parameter (even `"not-a-model"` returns 200), take about 1.6 s to first audio, and honour pace but not pitch or loudness. A cloned voice is therefore not V4 Flash and cannot carry the tone dial. Voice banking stays as an optional, consent-gated extra.

**4. Overruled the brief: corrected the numbers.** "AAC users average 15 wpm" is the speech recognition figure in Koester and Arthanat 2018. We say "typically under 10 wpm, 1.7 wpm with switch scanning". SpeakFaster's "57%" is "57% more motor action savings in offline simulation", not fewer actions for real users. "Voice banking needs 50 to 3,200 sentences" is out of date (Apple now asks for 10 phrases). Sources in [research/evidence.md](research/evidence.md).

**5. Overruled the brief: we do not claim to be first.** Partner-aware reply suggestion exists (Converser 2008, Lingraphica Conversations, Voixa, SpeakFaster). We claim only what we checked: no prior art found for prespeaking every option in AAC.

**6. Draft while they talk.** Kanth drafts and voices replies from Saaras partial transcripts while the partner is still speaking, redrafting as the sentence grows (at most three times per turn). When the final transcript arrives, the drafts are kept if it added little, otherwise Kanth drafts again. Word counts are compared rather than words, because partials are plain transcription while the final is code-mixed. Measured in the app run locally (9 turns, [bench/results/live-app.json](bench/results/live-app.json)): all four replies on screen a median 95 ms after the partner finished, and before they finished in 3 of 9 turns (up to 0.66 s early). This answers "you pre-render, so why Flash?": Flash gets four voiced replies ready within about a second of the partner stopping, sometimes before. It costs more API calls, so it can be switched off.

**7. Keyword steering.** Our first benchmark found the drafts matched the user's intent in only 5 of 36 turns. When no draft fits, typing one or two words redrafts all four around them. This is how shipping AAC bridges misses, and it costs a fraction of typing the full reply.

**8. Tone changes words and voice.** Each tone maps to Bulbul pace, pitch and loudness, prefers a matching persona style where the voice has one, and changes the wording the model drafts. Measured: loudness separates the five tones cleanly; pitch and rate move in the right direction but overlap, partly because Bulbul output varies between identical requests. Reported as measured.

**9. The always-ready board works offline.** The default emergency phrases ship as audio pre-generated with Bulbul ([scripts/make-static-audio.ts](scripts/make-static-audio.ts)); others are synthesized once and stored in IndexedDB. All are loaded into memory at start. A service worker caches the app shell. The film cuts the network for real and the board still speaks.

**10. Fictional demo user, clearly labelled.** Arjun is fictional. Every voice in the demo is generated by Bulbul. No real person's voice or words are used anywhere.

## Technical

**11. Stack: one Node and TypeScript server, a React client built by Vite, one package.** The key must stay on a server, judges must run it with one command, and the browser needs Web Audio and the microphone. No framework on the server: `node:http` plus `ws`.

**12. Bulbul transport: a pool of four warm WebSockets.** Measured: four replies on four warm sockets finish in about 484 ms, against 794 ms for four parallel REST calls and 1,667 ms queued on one socket. A cold connection once took 7.2 s to open, so sockets are opened at start and kept alive with pings. Fallback order: WebSocket, then HTTP streaming, then REST, then the device's own voice, with a visible notice at each step.

**13. Audio format: 24 kHz PCM16 end to end.** The server asks Bulbul for `linear16` and forwards chunks to the browser, which schedules them gaplessly with Web Audio. Prespoken replies are decoded in advance, so choosing one starts sound on the next audio frame. Measured choice to audible: 50 to 58 ms ([bench/results/live-app.json](bench/results/live-app.json)), nearly all of it the browser's reported output latency. It was not measured acoustically, and Bluetooth or phone speakers can add more.

**14. Drafting model: `sarvam-105b-conversations`, thinking off.** Measured: four drafts in 300 to 450 ms, about twice as fast as `sarvam-105b` (about 1 s). Sarvam-M is deprecated. The prompt asks for native script per language, English words in Latin, one format example in the reply language only, and no names except the addressee's.

**15. Speech recognition: Saaras realtime with `codemix` output.** Code-mixed finals keep English words in Latin script, which is exactly what Bulbul wants. The demo knows exactly when the partner stops, so it uses manual endpointing: finals arrive a median 287 ms after the end (206 to 348 ms, [bench/results/live-app.json](bench/results/live-app.json)). The live microphone uses server VAD.

**16. Why V4 Flash when v3 was faster to first audio in our tests.** Measured from India: v3 warm WebSocket p50 244 ms, V4 Flash 304 ms. We still chose V4 Flash because the tone dial needs pitch and loudness (v3 takes pace only), because persona styles give each tone a different delivery, because it costs less per character, and because Sarvam is retiring v3 for voice agents. With prespeak, the user never waits for first audio either way.

**17. Runaway audio guard.** Bulbul once returned 57.8 s of speech for a 42-character reply. The server now cuts any utterance longer than 3 s plus 0.3 s per character.

**18. Partner voices in the demo.** Bulbul has no female Tamil persona, so Amma is voiced by `kavitha_te_conversation` speaking Tamil. Saaras transcribed her accurately, which we took as a sanity check. Arjun's Tamil replies use `vijay_ta_narration` because the `shubh` voice has no Tamil persona. The UI says when a voice was substituted. This is in our note to the Bulbul team.

**19. Access methods.** Touch and number keys; one switch (automatic scanning that jumps straight into the replies when they arrive, and stops after three silent loops to avoid fatigue); two switches; dwell with a visible fill bar; and blink, using MediaPipe Face Landmarker on the device, where a deliberate blink longer than a natural one acts as the switch.

**20. Design.** A soft, tactile interface: raised controls you can press, recessed areas that hold content, a sliding tone dial, and an orb that moves with the real audio level. Classic soft UI has poor contrast, so text stays at AA contrast or better, the scanning highlight is a thick outline that reads from across a room, and the high contrast theme is flat.

**21. A guarded public demo, at the owner's request.** We first decided against a public URL, because it puts a key-backed endpoint on the internet. The project owner asked for one on Vercel, so it runs with guards: requests must come from Kanth's own page, each visitor is rate limited, text and audio sizes are capped, and voice cloning is off. The rate limits are counted in memory in each running function instance, so they reset on a cold start and are not shared between instances; they slow down casual abuse, not a determined attacker. Vercel functions cannot hold Kanth's WebSocket, so the hosted build uses an HTTP transport with the same messages ([web/src/lib/http-transport.ts](web/src/lib/http-transport.ts), [server/hosted.ts](server/hosted.ts)). Every endpoint is served by one combined function, so one warm instance answers them all; it is bundled with the Build Output API ([scripts/build-vercel.mjs](scripts/build-vercel.mjs)) and pinned to the Mumbai region near Sarvam. The partner's demo lines and the default emergency phrases ship as static audio pre-generated with Bulbul, so the demo starts at once; every reply the user can choose is still drafted and voiced live. If Sarvam cannot be reached, the demo replays a recorded real run and says so ([web/src/lib/replay-transport.ts](web/src/lib/replay-transport.ts)). It is slower before the choice (no warm sockets; partial transcripts come from re-sending the audio so far about every 0.7 s instead of a stream, so drafting can still start while they talk) and identical at the choice: about 50 ms to the voice. Measured on the live site: all four voiced a median 1.6 s after the partner stopped ([bench/results/live-hosted.json](bench/results/live-hosted.json)). The microphone works there too: the browser detects each turn's end with an adaptive energy detector (1 s of quiet ends a turn, 0.8 s of audio before the start is kept), drops audio while Kanth is speaking, and merges speech that resumes within 4 s into the same turn.

**22a. What the hostile review changed.** We ran a review as the harshest Sarvam judge and as an AAC user with ALS who uses one switch. It found that holding the switch for a second spoke a reply nine times, that a switch press with Settings open acted on the page behind it, that the device voice fallback claimed to speak Tamil on a device with no Tamil voice, that replies could change under the scan highlight, and that one switch users had no way to steer. All are fixed: key repeat is ignored and selections lock out briefly, scanning pauses while Settings is open, the fallback reports honestly and shows the reply full screen when nothing can speak it, redrafts swap in at once and recent changes block choices, and a Yes, No, Not now, Ask them back and 0 to 10 row lets a switch user steer. The first film had Arjun give a pain score the model invented; the film now shows him giving the number himself. The interactive demo's drafts could still state a number, which 22c addresses.

**22b. The benchmark result we did not want, published as is.** On a blind held-out set, a draft said what the user meant in 12% of turns, and 25% after one steering press. Motor actions fell by only 1 to 2% overall. We report this in the README rather than tuning the test set, and we pitch Kanth as the instant path when a draft fits, never a replacement for typing.

**22c. What the second review changed.** A second review, as a Sarvam judge, a claims auditor and an AAC user, found problems the first did not. The fixes:

- **Number guard.** The drafts are told never to invent symptoms, but in a live run one offered a pain score nobody had given. Now, when the partner asks for a number and the user has not steered with one, any draft that states a number is dropped in code, so the number comes only from the user's own press on the 0 to 10 row or their typing. The demo's simulated chooser no longer prefers drafts with numbers.
- **Name guard.** Drafts still called an unknown speaker "Amma" and named people from earlier scenes. Now a draft that names someone from the profile other than the person speaking, unless the partner mentioned them, is dropped in code; when the speaker is unknown, so is any draft that calls them by a name or a title such as Amma or Doctor.
- **The microphone is always stoppable,** and it stops when you leave the conversation. Before, once it heard a line there was no stop button, and it kept sending audio after you left.
- **Emergency phrases first.** The emergency board now sits at the top of the side panel, on the first screen of a desktop. A one switch user reaches it by holding the switch, and a dwell user by dwelling on it; before, dwell worked only on reply tiles and the board sat behind the replies.
- **A press during the reply lock no longer drops emergency phrases.** Before, a switch press on Suction in the moment new replies arrived was silently ignored.
- **A cancelled reply is never spoken later by the device voice.** Before, a reply cancelled while its Bulbul audio was still on the way could still be spoken by the fallback voice.
- **A stopped reply is not counted as said.** It is no longer logged, sent to the model as context, or treated as the end of the turn.

The held-out benchmark (above) and the live measurements in the README were run before the number and name guards.

**22. Sarvam docs MCP server not connected.** It would not load into a running session. We read the same content through `llms.txt` and the `.md` version of each page, and recorded every place the docs and live behaviour disagree in [research/sarvam-api.md](research/sarvam-api.md).
